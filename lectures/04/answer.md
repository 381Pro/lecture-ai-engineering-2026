## 宿題

- 取り組んだレベル：発展
- やったこと：
  - ベンチマークとして SWE-bench Verified を調べた。データセット名は SWE-bench Verified（princeton-nlp/SWE-bench_Verified）。URL は https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified 。
  - 問題を 3 件読んだ（全文は貼らず、要約で書く）。
    - django__django-15572：Django 3.2.4 以降、TEMPLATES 設定の DIRS に空文字（''）が含まれると、開発サーバーの自動リロード（autoreload）が動かなくなる不具合。3.2.4 でテンプレートディレクトリの扱いが pathlib.Path による正規化に変わったため、template_changed() が常に True を返すようになり、アプリのコードを変更してもリロードされなくなった。修正は、autoreloader のテンプレート変更チェックで空の名前のディレクトリを無視すること。
    - astropy__astropy-12907：ネストした複合モデル（CompoundModel）で、separability_matrix（分離可能性の行列）の計算が誤っていた。& 演算子の右側に複合モデルがある場合に分離可能性が正しく計算されない。修正で、ネストした複合モデルの分離可能性を正しく計算するようにした。
    - astropy__astropy-13033：TimeSeries で必須カラムのチェックが失敗したときの例外メッセージが誤解を招くものだった。lightkurve のように _required_columns を上書きして flux / flux_err を含める場合に、何が起きているのか分からないメッセージが出ていた。修正で、必須カラムに関する例外メッセージを分かりやすくした。
  - 作問・検証の人数と手順を調べた。93 名の Python 開発者が、SWE-bench の中から 1,699 件の問題を人手で検証した。1 件あたり 3 名が別々にラベル付けを行い、問題文が不十分なものやテストで合否を判定できないものを除外した。68.3% を除外し、残った 500 件を SWE-bench Verified として選抜した。
- 結果：
  - 演習の評価セット（10 件、講師 1 人が作成、人と LLM で採点）との違いは次の通り。
    - 規模：演習は 10 件で、SWE-bench Verified は 500 件。
    - 作問者：演習は講師 1 人が問題文・回答・期待するふるまいを仕込んで作ったもの。SWE-bench Verified は実際の GitHub の issue と、それを修正したプルリクエストから作られている。
    - 検証の人数と方法：演習は講師 1 人のラベルが正解で、自分のラベルと比べるだけだった。SWE-bench Verified は 93 名の開発者が 1 件あたり 3 名で検証し、選抜した。
    - 判定の方法：演習は人（自分）と LLM が 5 つの基準で T/F/unsure を付ける採点で、要確認の扱いもあった。SWE-bench Verified はテスト（FAIL_TO_PASS / PASS_TO_PASS）で合否を自動判定し、問題の正解はプルリクエストのパッチとテストである。
    - 問題の種類：演習の問題は講師の回答の良し悪しを見るための作問で、SWE-bench Verified の問題は実際のバグ修正である。
- 気づき・疑問：
  - 演習の 10 件は講師が失敗を仕込んだ作問なので、どこが悪いかを見つける練習になった。一方 SWE-bench Verified の問題は実際のバグで、問題文が長く、前提知識も必要になる。評価セットの作り方で、測れるものが変わると感じた。
  - SWE-bench Verified の検証では 68.3% もの問題が除外されている。人手で 3 名ずつ確認して半分以上を落とすのは大変だが、ベンチマークの信頼性のためには必要な作業だと思った。
